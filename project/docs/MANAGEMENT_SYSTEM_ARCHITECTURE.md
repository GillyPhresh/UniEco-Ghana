# UniEco Ghana Management System — Architecture Audit

Audit baseline: repository/worktree on 2026-09-30. This document describes code and migrations present in the workspace; it does **not** claim those migrations have been applied to staging or production.

## Current architecture

### Routes and shell

Management currently lives under `/admin` and is built from client-rendered pages wrapped by `AdminRouteGuard` and `AdminLayout` in `components/admin/admin-layout.tsx`. The shell and `lib/auth/permissions.ts` provide display/navigation affordances only. The server middleware in `lib/supabase/middleware.ts` validates the Supabase user, resolves `current_app_role()` from the database, and blocks unapproved `/admin` routes before rendering:

- `super_admin`: all existing `/admin` pages.
- `moderator`: an operations overview when at least one operational capability is assigned; moderation, verification, support, communications, event, review, and advertising routes require their matching database `has_permission(...)` capability.
- `university_admin`: a separate `/admin` overview plus `/admin/universities`, read-only `/admin/orders`, `/admin/search`, `/admin/businesses`, scoped student routes, and `/admin/announcements`. The university overview uses a dedicated membership-derived aggregate RPC; it never receives the platform-wide summary or financial figures. The order, search, business-directory, student-directory, announcement, and dashboard RPCs independently apply database-derived `can_manage_university()` scope; route admission alone never grants cross-university data. The business directory omits owner email for university admins, announcements use an allowlisted trusted audit helper, and platform-wide announcements remain super-admin-only.
- `moderator`: the navigation queries the existing `has_permission(...)` checks to show only sections granted to that account. This is display-only; middleware and RPCs independently enforce the matching server-side checks.
- other roles and lookup failures: denied.

Protected page responses are marked `private, no-store`. API handlers must still authenticate and authorize independently; the middleware route check is not their authorization boundary.

### Identity, roles, and tenant scope

The existing authority model is database-backed: `profiles.role_id` references `user_roles`; `current_app_role()`, `is_super_admin()`, `is_staff()`, `has_permission()`, and `can_manage_university()` are the established helpers. University scope is represented by `university_admin_memberships`, with active membership checked by `can_manage_university()`. Platform-role transitions and university administrator assignment use the A1 server/database procedure architecture; browser role metadata is not trusted.

`lib/auth/permissions.ts` explicitly describes its static mapping as UI-only. It must not be used as a substitute for RLS, trusted RPC authorization, or server authorization. The `/admin/roles` screen retains that reference matrix and exposes a narrow moderator-capability editor. Draft migrations `0068` and `0074` read/write the existing `role_permissions` table only through super-admin-only RPCs, limit edits to report review, verification review, support, and content moderation, require a reason, and record changes through the trusted audit logger. This is not a general role/permission editor and cannot grant super-admin authority.

### Sensitive mutation and audit architecture

The existing A2/A3 foundation contains resource-specific procedures and database rules for role changes, profile status, university records/branding, vendor verification, orders, subscriptions, payments/reconciliation, advertisements, reports, support, CMS, announcements, communications, reviews, and delivery operations. `record_trusted_admin_action(...)` derives the actor from `auth.uid()` and writes administrative and audit records. Protected table writes were consolidated in migration `0038`; direct browser updates are not a replacement for its narrow RPCs.

Financial state remains database/provider-authoritative. Paystack initialization and webhook verification are server-side, providers default disabled, and the browser must never declare a payment successful. Private verification documents are accessed through the document-ID authorization and short-lived signed-URL workflow; do not use public URLs for those documents. The private communications queue is service-role controlled and browser code must not dispatch providers.

## Security and reliability findings

1. Client-side route guards and role maps are not security boundaries. Middleware and each database function/API must independently authorize.
2. University scope must be resolved from the current authenticated database identity. Query parameters, client scope lists, and hidden controls are not authority. The new university listing function uses `can_manage_university()`; underlying staging RLS/RPC behavior still needs real cross-tenant integration tests.
3. Financial figures must not be computed by downloading payment amounts into browser JavaScript. The new finance summary and export functions are intended to preserve database aggregation and audit authority.
4. Empty data and query failure are different states. The updated dashboard, finance, health, and university list fail visibly rather than translating query errors into zero counts or empty success states.
5. Financial row access must be narrower than general staff access: the management readers omit provider/webhook/mobile/failure details, while the database limits payments, payment history, transaction audit, and coupon-redemption RLS to super admins and preserves each user’s own payment access.
6. System health must distinguish measured health from disabled, unavailable, or unmeasured dependencies. A successful authenticated RPC proves the database request worked; it does not prove external provider, storage, or Edge Function availability.
7. Static tests are useful regression guards but do not prove RLS behavior, SQL execution, browser flows, or isolation between actual tenant accounts.
